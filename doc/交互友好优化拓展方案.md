# 邮箱聚合插件 · 交互友好优化拓展方案

> 版本：v1.0　｜　审查范围：`one-email-plugin` 前端（React 19 + Zustand 范式 Hook + IPC 封装）
> 定位：在**不影响现有功能、不重复造轮子、不产生代码冗余**的前提下，提出面向"用户交互友好度"的增量优化清单。
> 本文档仅作方案评审，**不落地代码**。每项均标注现状、痛点、方案、复用点与回归风险，供后续按优先级实施。

---

## 一、审查结论概览

插件当前已具备较完整的邮件聚合能力（多账号、统一收件箱、全文搜索、IMAP IDLE 实时推送、分类筛选、文件夹管理、草稿、签名、OAuth2、暗色模式）。交互层面存在两类可优化空间：

1. **功能缺口**：协议契约已预留、但 UI 未接上的能力（附件上传、密送 Bcc），补齐即高价值；
2. **体验短板**：纯前端即可改善的交互细节（关闭未保存提醒、上一封/下一封导航、键盘导航、自动存草稿、远程图片按需加载等）。

## 二、P0（强烈推荐：纯前端、高价值、零协议扩展）

### 1. 写信附件上传

- **现状**：`types/index.ts` 已定义 `ComposeMail.attachments`（`{ filename; content; contentType? }[]`），主进程 `sendMessage` 的 mail 参数也包含该字段（基于 nodemailer，天然支持附件）；但 `Compose.tsx` **没有任何附件选择 UI**，该契约处于"半成品"状态——用户无法在写信时附带文件。
- **方案**：
  1. `Compose` 增加「添加附件」按钮 + `<input type="file" multiple hidden>`；
  2. `FileReader.readAsArrayBuffer` 读取，构造 `{ filename, content: ArrayBuffer, contentType: file.type }`，追加到本地 `attachments` state（含大小、文件名列表，可逐个移除）；
  3. 发送时把 `attachments` 透传进 `ComposeMail.attachments`；
  4. 附件列表 UI 复用 `AttachmentBar` 的视觉风格（或抽一个只读列表），避免重复样式。
- **复用点**：`ComposeMail.attachments` 类型、`sendMessage` 契约、`formatSize`（展示大小）。
- **前置验证**：发一封带附件的测试邮件，确认主进程 `sendMessage` 已正确消费 `attachments`；若主进程未实现，则此项升级为"需主进程小改"。
- **回归风险**：仅新增字段与 UI，不影响纯文本/富文本发送链路；需保证无附件时 `attachments` 为 `undefined` 以维持旧行为。

### 2. 写信关闭未保存提醒（脏检测）

- **现状**：`Compose` 的「关闭」按钮直接调用 `onClose()`，用户误点关闭即丢失全部输入。
- **方案**：
  1. `Compose` 初始化时保存一份初始快照 `initialRef = { to, cc, subject, bodyHtml }`（草稿模式下为草稿原文）；
  2. 关闭时对比当前值与快照，若有差异（`trim` 后比较，忽略空白）则弹 `Modal` 二次确认：「放弃编辑 / 继续编辑」；
  3. 发送成功后正常关闭（不发提示）。
- **复用点**：现有 `Modal` 组件。
- **回归风险**：无；仅包裹关闭逻辑。注意草稿打开后直接关闭（未改动）不应误报。

### 3. 阅读区「上一封 / 下一封」导航

- **现状**：`MailReader` 只有回复/转发/标未读/移动/删除，读完一封要回到列表手动点下一封。
- **方案**：
  1. 在 `ToolPanel` 层（或 `MailReader` 新增两个回调）基于**当前可见列表**（`visibleMessages` 与 `MailList` 的过滤口径一致）计算 `selectedDetail.uid` 的 index；
  2. 「上一封 / 下一封」调用现有 `onSelect(m)`，触发 `openMail`，自动标已读并加载正文；
  3. 边界：首/尾禁用对应按钮。
- **复用点**：`activeMessages` + 现有 `onSelect` 链路，零新增服务。
- **回归风险**：需与「搜索态」「未读筛选态」下的列表顺序保持一致（直接用渲染层同一份过滤结果，避免口径不一致）。

### 4. 列表键盘导航（Gmail 风格）

- **现状**：`MailList` 无任何键盘事件，重度用户只能纯鼠标操作。
- **方案**：
  1. `MailList` 容器 `tabIndex={0}` + `onKeyDown`，维护 `activeIndex` 高亮（与 `selectedUid` 高亮解耦或合并）；
  2. 键位：`J`/`↓` 下一封、`K`/`↑` 上一封、`Enter` 打开、`Delete`/`Backspace` 删除当前、`N` 写邮件、`E` 归档/移动（可选）；
  3. **防劫持**：当焦点在 `input/textarea/contentEditable` 或搜索框时，直接 return，不拦截；多选模式（selectionMode）下禁用方向键导航避免语义冲突。
- **复用点**：`onSelect`、`onDelete`、`onCompose` 等现有回调，仅新增事件监听与索引态。
- **回归风险**：需严格控制"何时劫持按键"，否则会干扰写信输入；建议统一抽一个 `isTypingTarget(e.target)` 判断函数，避免多处重复。

## 三、P1（推荐：纯前端为主，部分需主进程小扩展）

### 5. 草稿自动保存

- **现状**：需手动点「存草稿」，中断后内容丢失。
- **方案**：`Compose` 内 `bodyHtml/to/cc/subject` 变化时，防抖（2s）自动 `draftService.upsertDraft`；首次自动保存时生成 draft id 存入本地。与「手动存草稿」共用一个 `upsertDraft`，互不冲突。
- **复用点**：`draftService`（localStorage）整套读写。
- **注意（避免冗余）**：自动保存与脏检测共用同一份"是否有未保存变更"判定；发送成功后删除对应草稿；不要为自动保存另建一套草稿存储。

### 6. 收件人自动补全（联系人记忆）

- **现状**：写信时收件人需手动完整输入，无历史联想。
- **方案**：
  1. 新建轻量 `services/contactService.ts`，复用 `draftService` 的 localStorage 读写范式，维护 `{ email, name, count, lastSeen }[]`，条数上限（如 500）淘汰最久未用；
  2. 数据来源：`openMail` 成功后记录 `detail.from / to / cc`（不记录正文），及发送成功后的 `to/cc/bcc`；
  3. 写信「收件人 / 抄送 / 密送」输入框输入时，按前缀匹配邮箱或姓名，下拉候选，点击/回车填充。
- **复用点**：localStorage 模式、`Address` 类型。
- **注意**：这是**新增能力而非造轮子**（插件现无任何联系人能力）；但需控制体量，只做"联想填充"，不扩展为完整通讯录模块（那会与主程序通讯录系统重复）。

### 7. 密送 Bcc 字段

- **现状**：`ComposeMail.bcc` 契约已定义，但 `Compose` 只有收件人 / 抄送两栏。
- **方案**：新增「密送」输入框，发送时拆分为数组写入 `mail.bcc`。
- **复用点**：`ComposeMail.bcc`、与 `cc` 相同的拆分/校验逻辑（抽公共函数，避免复制粘贴）。

### 8. 收件人 / 抄送邮箱格式校验

- **现状**：仅校验"非空"，格式错误的地址会直接发信失败或静默丢弃。
- **方案**：发送前对 `to/cc/bcc` 拆分后的每个地址做轻量邮箱正则校验，非法地址高亮/列出并阻止发送（提示"存在无效地址：xxx"）。
- **复用点**：发送前校验流程；抽一个 `splitAddresses / isValidEmail` 工具（可放 `utils/format.ts` 或新建 `utils/validate.ts`），供收件人/抄送/密送三处共用。

### 9. 远程图片按需加载开关（隐私友好）

- **现状**：`MailReader` 用 `DOMPurify.sanitize` 时 `FORBID_TAGS: ['img', ...]`、`FORBID_ATTR: ['src', ...]`，一刀切禁掉所有图片——既防追踪，也让正常图片邮件显示不完整。
- **方案**：
  1. 默认维持现有严格策略（不加载任何远程内容）；
  2. 正文顶部加「显示图片」按钮，点击后改用放行 `<img src>` 的 sanitize 配置重新清洗并重渲染 iframe；
  3. 放行时仍保留 `FORBID_TAGS` 中的 `script/iframe/object/embed/style` 等，并对 `img src` 做 `ALLOWED_URI_REGEXP`（仅 `http/https`，禁止 `data:`/`javascript:`）。
- **复用点**：`DOMPurify` 现有实例与 `cleanHtml` 的 `useMemo`，仅将 sanitize 配置参数化。
- **回归风险**：安全边界不可突破——放行后的白名单必须严格；开关状态随邮件切换重置为"不加载"。

### 10. 星标邮件（\Flagged）

- **现状**：`MailMeta` 无 `flagged` 字段，列表无法表达"重要/星标"。
- **方案**：
  1. 主进程 `listMessages` 返回值新增 `flagged: boolean`（`getMessage` 可选同步）；
  2. 前端在列表行加星标图标（点击切换），调用 `emailService.setFlags({ ..., add, flags: ['\\Flagged'] })`；
  3. 新增「星标」筛选（可选）。
- **复用点**：`setFlags` 已是通用接口（`setSeen` 就在用它），**无需新增 IPC**；`MailMeta` 仅加一个字段。
- **回归风险**：主进程改动为"新增可选字段"，对旧数据/旧契约兼容。

### 11. 列表「仅带附件」快捷筛选

- **现状**：`MailMeta.hasAttachment` 已返回，但列表筛选只有 全部/未读/已读。
- **方案**：`MailFilter` 扩展一个 `attachment` 值，或在工具栏加一个「附件」快捷过滤按钮，前端 `messages.filter(m => m.hasAttachment)`。
- **复用点**：现有 `visibleMessages` 过滤链路 + `hasAttachment` 字段，零协议改动。

### 12. 邮件列表摘要（snippet）

- **现状**：列表只显示 发件人/主题/时间/账号，无法在列表层快速判断内容。
- **方案**：主进程 `listMessages` 返回 `snippet`（正文前 ~80 字纯文本），列表行在主题下方灰显单行摘要。
- **复用点**：`MailList` 现有行布局，仅追加一行文本。
- **回归风险**：属主进程扩展（新增字段，兼容），需在服务端 fetch 时避免额外拉全量正文（用 IMAP BODY[HEADER] + 截断或 `ENVELOPE` 之外的轻量方式，或仅在详情打开后回填缓存摘要）。

## 四、P2（可选：跨账号 / 依赖主程序或需权衡）

### 13. 统一收件箱批量操作

- **现状**：统一收件箱提示"暂不支持批量操作"，仅能单封删除。
- **方案**：批量选中后按 `accountId` 分组，逐账号调用现有 `deleteMessages/moveMessages`，聚合 Promise 结果。
- **注意**：跨账号失败需逐条反馈（哪封失败、哪个账号），交互复杂度上升；建议作为后续增强而非当前必做。

### 14. 搜索范围扩展

- **现状**：全文搜索仅限**当前文件夹**。
- **方案**：增加"当前文件夹 / 全部文件夹"范围切换；"全部"需主进程对每个文件夹执行 SEARCH（成本随文件夹数线性上升，需做并发上限与去抖）。
- **依赖**：主进程 `searchMessages` 支持跨文件夹，或前端循环文件夹逐一调用。

### 15. 记住上次账号与文件夹（状态持久化）

- **现状**：每次打开插件都回到默认账号 / 收件箱。
- **方案**：`useAccountStore` 初始化后，从 localStorage 读 `lastAccountId / lastFolder`，校验存在后恢复；切换时写回。
- **复用点**：可并入现有 `config/settings`（`storageService`）或独立 localStorage key，避免与 config 结构强耦合。

### 16. 新邮件轻提示 toast

- **现状**：新邮件仅更新侧栏未读角标，无显式提醒。
- **方案**：`onNewMail` 回调中 `addToast`（"收到新邮件"），并做**设置开关**（默认关，避免多账号高频打扰）。
- **注意**：`onNewMail` 是"单订阅覆盖式"，需确认与现有 `ToolPanel` 统一订阅逻辑兼容（当前已集中订阅，只需在 handler 内追加提示）。

### 17. 系统通知 / 全局快捷键 / 任务栏角标

- **说明**：需 ToolBox **主程序**配合（Electron Notification / globalShortcut / Badge），超出插件前端职责。
- **建议**：由 ToolBox 主程序提供 `window.electron.email.notify` 或通用通知通道后，插件再接入；当前**不重复实现**通知系统。

### 18. 归档 / 导出 .eml

- **归档**：IMAP 无统一语义（Gmail=移除 INBOX、其他=移特定文件夹），跨服务商行为不一致，建议暂缓。
- **导出 .eml**：需主进程返回原始 MIME 源文，前端触发下载；价值低、依赖主进程，暂缓。

## 五、明确"不做"清单（防造轮子 / 防冗余）

| 不建议做 | 理由 |
|---|---|
| 引入 `react-window` / 虚拟滚动 | 现有 50 封/页 + 「加载更多」已够用，虚拟化是过度设计，增加依赖与体积 |
| 换装重型富文本编辑器（Slate / Quill / TipTap） | 现有 `execCommand` 已满足写信基本排版，换库引入大量代码与冗余 |
| 新建"联系人"独立模块 / 数据库 | 与主程序通讯录系统职责重叠；本方案仅做轻量联想记忆（见 P1#6） |
| 再建一套确认弹窗 / Toast | 已有 `Modal` / `Toast`，所有新交互直接复用 |
| 前端自研 IMAP/SMTP 协议层或本地缓存层 | 协议已在主进程（imapflow/nodemailer/mailparser），前端重复触网属架构倒置 |
| 无差别开启新邮件系统弹窗 | 高频打扰，违背"友好"，需默认关闭 + 开关 |

## 六、落地建议

1. **实施顺序**：先做 P0（1→4），均为纯前端、可独立验证、互不耦合；再做 P1 中零协议改动的项（5/6/7/8/9/11），最后评估需主进程配合的项（10/12）。
2. **批次验证**：每批完成后执行"构建通过 + 冒烟"再进入下一批，避免堆积未验证代码。
3. **回归测试重点**（改动后需覆盖）：
   - 账号切换 / 凭据解密链路不回归（P0 改动不触碰 store 数据流）；
   - 统一收件箱与单账号视图的分派逻辑（`isUnified` 分支）不被新交互破坏；
   - 搜索态 / 多选态 / 未读筛选态下，新增导航与筛选口径一致；
   - 键盘导航不得劫持写信输入框、搜索框的按键；
   - 远程图片开关不破坏 DOMPurify 安全边界。
